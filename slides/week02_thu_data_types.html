Your turn: fix the type error

The depth was read from a text file, so it’s a string. Fix the calculation so it produces a number.

Hint

There’s a builtin that converts a string to a floating point number. It’s named after the type it produces.

Solution

depth_below_datum = float(depth_text) + 12.0

Gives 57.7. Note int("45.7") would fail — int() won’t parse a decimal point out of a string. int(float("45.7")) works and gives 45.

Floats are approximations

Not a bug. 0.1 has no exact binary representation, exactly as \(\tfrac{1}{3}\) has no exact decimal one.

Never test floats with ==. Test whether the difference is small enough:

\[|a - b| < \epsilon\]

This is precisely how you’ll decide an iterative solver has converged in Week 4.

Sequences

Lists

An ordered, changeable collection. Square brackets.

Indexing starts at zero. [0] is the first element. [-1] is the last, which is genuinely useful — no len(x) - 1 arithmetic.

Slicing

sequence[start:stop] — includes start, excludes stop.

Half-open intervals feel wrong for about a week, then feel right forever: a[:n] and a[n:] split a sequence with no overlap and no gap, and stop - start is always the length.

Your turn: slice a timeseries

monthly_head holds one head measurement per month for a year, January first. Pull out the summer monsoon months — July, August, September.

Hint 1

January is index 0, so what index is July?

Hint 2

You want three elements starting at index 6. Remember the stop index is excluded, so it needs to be one past the last element you want.

Solution

monsoon = monthly_head[6:9]

[409.1, 411.7, 413.9] — the recovery after the June low, which is what monsoon recharge looks like in a hydrograph.

Lists change, tuples don’t

grid_shape[0] = 5
# TypeError: 'tuple' object does not support item assignment

Use a tuple when the collection is one thing — a coordinate, a grid shape, a row. Use a list when it’s a growing pile of things. MODFLOW grid shapes come back as tuples, and that’s not an accident.

Dictionaries

Look things up by name instead of position.

aquifer["storativity"] would raise KeyError. .get() with a default is how you handle data that might be missing — a Week 6 problem you’ll meet a lot.

Your turn: build a lookup

Build a dictionary mapping each well ID to its hydraulic conductivity, then look up well "B-07".

Hint 1

You could type the dictionary out by hand — {"A-14": 12.4, ...} — and that is a perfectly good answer.

Hint 2

For the slicker version: zip() pairs up two sequences, and dict() turns a sequence of pairs into a dictionary.

Solution

By hand:

k_by_well = {"A-14": 12.4, "B-07": 3.8, "C-22": 41.0}

Or built from the two lists:

k_by_well = dict(zip(well_ids, conductivities))

Both give 3.8. The second scales to 3000 wells; the first doesn’t. We come back to zip() next week.
